Slack bot that explains what happened to a booking

  • n8n
  • Slack API
  • LLM
  • Data tables

ProblemWhen a guide, price or balance changed on a booking, the reason sat in a long audit log that only a few people could read. Support and ops waited on the tech team for every answer.

What I builtAnyone mentions the bot with a booking reference and a question. It reads the booking's full history without any ability to change it, parses every entry, and replies in the thread with the cause. Follow-up questions continue in the same thread without another mention. I extended the same pattern to product and promotion logs.

Design choice: strictly read-only, so the bot can explain a booking but can never alter one.

  1. @mention in Slack
  2. Extract booking ref
  3. Read-only log fetch
  4. Parse history
  5. LLM explains cause
  6. Threaded reply

Google review replies across a dozen business profiles

  • n8n
  • Google Business Profile API
  • Monday.com GraphQL
  • LLM
  • Slack

ProblemReplying to Google reviews meant checking each business profile by hand. Reviews with a star rating but no text, and reviews logged but never answered, slipped through.

What I builtOne hourly poller that replaced a separate workflow per location. It reads the list of live locations from a Monday.com board, so adding a location means adding a row. A shared review agent removes duplicates against the board, logs each review, decides whether it needs a reply (including star-only reviews), drafts one with an LLM, posts it through the Google API, and writes the outcome back to the board and Slack. Every failure branch raises a Slack alert.

Debugging worth noting: I traced a silent loss of items (50 in, 34 out) to a built-in node that batched many lookups into one call, and a sub-workflow that returned only its last branch. I replaced both with direct API calls and an explicit merge step.

  1. Hourly schedule
  2. Live locations from Monday
  3. Fetch reviews
  4. De-duplicate + log
  5. LLM drafts reply
  6. Post to Google
  7. Outcome to board + Slack

BuildHawk, a multi-agent AI employee hub

  • Demo · sample data
  • n8n
  • OpenAI
  • Data tables

ContextA prototype I built on my own with sample data, for a construction-tech brief. Not a deployed client system.

ProblemThe brief wanted three AI "employee" bots — operations, contract admin and finance — that could draft work but never act unsupervised, keep each client's data separate, and leave every money decision to a person.

What I builtA multi-agent system: three bots and a human approval queue behind a private hub. Contract Admin checks a request belongs to the right client, runs a budget check, and drafts a purchase order saved as pending; Finance reviews and recommends; a person approves or rejects, and every action is written to an audit log. Client separation is enforced on every record, and approval and bank actions are gated so a bot can draft but never approve or pay.

What I learned: a language model repeats whatever framing the data hands it, so the figures are computed in code and the model is forbidden to infer. It drafts; a human decides.

  1. Request
  2. Client check
  3. Budget check in code
  4. Draft PO, pending
  5. Human approval
  6. Audit log
